智能提醒
背景助手类产品以单条需求为单位创建提醒，且缺少记忆——用户需重复交代时间与事项，输入成本高。陪伴场景则不同：bot 可以在多轮对话中主动发起提醒，并可结合用户画像定制，承担延续对话的作用。用户需求往往隐含在多轮交流中，尤其在角色扮演场景下，玩笑表达与真实需求难以区分；同时，用户安排会随对话变化，静态提醒容易过时或与最新计划冲突。
方案
1.
多轮上下文提醒意图判定：结合用户 Query 与 Bot 回复进行提醒意图判定，识别对话中潜在的提醒需求；针对陪伴场景中的角色扮演和模糊表达，判断其是否对应真实提醒诉求，减少将玩笑或虚构情节误识别为有效提醒。
2.
上下文驱动的提醒动态维护：设计提醒更新模块，综合聊天历史与已有提醒列表，对提醒进行统一维护；每次执行时根据最新上下文判断提醒变化，支持提醒的新增、更新与删除，避免仅追加提醒造成的信息过期、重复及安排冲突。
3.
主动提醒与个性化触达：将提醒能力从被动指令响应扩展至对话上下文驱动的主动关怀，结合用户画像和对话中识别出的提醒需求，将提醒作为主动触达及后续对话延续的入口，通过后续提醒触达延续用户与 Bot 的互动。
效果线上回复率 31.4% → 66.17%（对比普通 push）；离线 benchmark 准确率 88%。
用户状态管理
项目背景在多轮对话场景中，用户不仅通过显式指令表达交互需求，也会通过连续对话中的反馈表现出兴趣变化、参与意愿等隐式状态。两类信号分别影响 Bot 的交互形式选择与话题推进策略，但原有链路缺乏统一的用户状态感知机制，难以从多轮上下文中提取并整合用户状态信息，导致下游策略缺少有效的决策依据。
核心方案
1.
双通路用户状态识别：将用户信号拆分为显式交互诉求与隐式对话状态两类，分别构建识别模块。显式模块识别图片、语音、唱歌等交互请求；隐式模块结合多轮对话上下文，识别用户对当前话题的兴趣变化及敷衍倾向，并将识别结果转换为结构化标签，供下游链路使用。
2.
Prompt 结构化增强：将训练 Prompt 拆解为语义独立的模块化 Part，为可变措辞维护等价表达集合，通过随机替换、重组构造多样化 Prompt，以提升语料多样性与模型泛化性、降低对固定模板和特定措辞的依赖。实现 parse_prompt / rebuild_prompt 两阶段处理：解析阶段抽取输出格式、对话历史等结构化字段；重建阶段仅对措辞类内容进行随机化，语义类字段保持原文，保证任务语义和训练样本标签一致。
3.
配置驱动的数据合成管线：将处理逻辑拆为幂等、可测的独立算子，用 YAML Recipe 编排多路数据 Pipeline（真实标注与意图库合成），统一汇聚至 Final 阶段产出训练集；引入内容指纹 Cache，未变更的数据直接复用处理结果，缩短数据构造与实验迭代周期。
4.
识别结果接入对话链路：通过模型微调增强对上下文语义及用户状态变化的识别能力；将两类识别模块部署在对话链路中间层，输出显式交互诉求与隐式对话状态标签，由下游模块据此调整交互形式、话题延展或话题切换。
A/B 累计实验收益新用户次日留存提升 1.64%、7 日留存提升 6.19%。

追打问题生成模型
背景单轮问答往往在给出答案后结束：用户不知道还能追问什么，会话轮次与停留时长都停在第一轮。业界普遍用主动生成追问承接下一步意图，把一次性问答变成多轮对话。
方案从 0 设计意图判定与生成链路：依据用户与模型的历史问答判断请求意图，微调混元-13B 生成多条追打问题，模型上线后持续迭代。
效果追打问题整体 badcase 率 39.3% → 14.77%。
浏览器阅读助手 Agent
方案以 ReAct 重构生成链路，降低模型调用与响应时延；接入联网搜索、天气、股价等工具，并判断文档问答何时需要联网补充；加入 Prompt 改写以支持多轮对话。
效果产品评估均分 82.00，线上基线 71.42。
